# API Contract — Referral System Integration (قرارداد بین‌سامانه‌ای ارجاعات)

**نسخه:** `v1`
**پیشوند:** `/api/v1/...`
**وضعیت:** طراحی تفصیلی (مبتنی بر ADR-015 و سند سامانه ارجاعات نسخه ۱.۱)
**تصریح‌دهی:** الگوی `Bearer JWT` معتبر IAM (طبق ADR-012 / DEC-027). سامانه ارجاعات باید توکن کاربر جاری یا توکن سرویس معتبر را در هدر `Authorization` ارسال کند.

---

## ۱. مقدمه و مرز مسئولیت

طبق **ADR-015**، سامانه ارجاعات یک سامانه مستقل است. این قرارداد مشخص می‌کند که سامانه ارجاعات برای موارد زیر **باید** از سرویس‌های `OrganizationalStructure` مصرف کند و منطق آن‌ها را پیاده‌سازی نکند:

1.  **تشخیص روابط سلسله‌مراتبی:** رئیس مستقیم، هم‌سطح‌ها، زیرمجموعه.
2.  **مسیریابی بر اساس مسئولیت:** یافتن پست و پرسنل مسئول برای یک کد مسئولیت (`ResponsibilityCode`).
3.  **دریافت ساختار سازمانی:** برای ساخت درخت دسترسی و نمایش نام واحدها.

## ۲. مدل‌های مشترک

### `PostDto` (از `posts.md`)
شامل `id`, `organizationId`, `code`, `title`, `parentId`, `isActive`, `hasSigningAuthority`, `responsibilities`, `authorities`.

### `EmployeeDto` (از `employees.md`)

## ۳. Endpointهای مسیریابی و ساختار (مصرفی توسط سامانه ارجاعات)

### ۳.۱. رئیس مستقیم — `GET /api/v1/posts/{id}/manager`
- **هدف:** یافتن پست والد (رئیس مستقیم) برای ارجاع به بالا.
- **پاسخ موفق (`200`):** `PostDto` پست والد.
- **پاسخ `404`:** اگر پست وجود نداشته باشد یا ریشه باشد (والد ندارد).
- **محدودیت:** فقط پست‌های فعال (`IsActive = true`) برگردانده می‌شوند.

### ۳.۲. هم‌سطح‌های مستقیم — `GET /api/v1/posts/{id}/peers`
- **هدف:** یافتن پست‌هایی که والد مشترک دارند (برای ارجاع افقی مجاز).
- **پارامترها:** `includeSelf=false` (اختیاری).
- **پاسخ موفق (`200`):** آرایه `PostDto`.
- **منطق:** تمام پست‌های فعال با `ParentId` برابر با `ParentId` پست مبدا (در همان `OrganizationId`).

### ۳.۳. زیرمجموعه (درخت) — `GET /api/v1/posts/{id}/subordinates?maxDepth=10`
- **هدف:** یافتن تمام پست‌های زیرمجموعه برای کنترل دسترسی «حق مسئولیت».
- **پاسخ موفق (`200`):** `PostTreeDto` (ساختار درختی).
- **کاربرد:** سامانه ارجاعات با داشتن این درخت، بررسی می‌کند که آیا پست مقصد در زیرمجموعه پست مبدا قرار دارد یا خیر.

### ۳.۴. مسیریابی مسئولیت — `GET /api/v1/responsibilities/{code}/resolve?organizationId={orgId}`
- **هدف:** پیاده‌سازی `FindResponsible(OrganizationId, ResponsibilityCode)`.
- **منطق:**
  1. یافتن `Responsibility` با کد داده شده.
  2. یافتن `PostResponsibilityAssignment` فعال در `OrganizationId` داده شده.
  3. یافتن `Post` منتسب.
  4. یافتن `EmployeePostAssignment`های فعال برای آن پست.
  5. برگرداندن پست و لیست پرسنل فعال به همراه `UserId`.
- **پاسخ موفق (`200`):** `ResolvedResponsibleDto`.
- **پاسخ `404`:** اگر مسئولیت یا انتساب فعالی در آن سازمان یافت نشد.
- **نکته مهم:** اگر چند پست در یک سازمان یک مسئولیت داشته باشند، این سرویس باید همه را برگرداند (یا بر اساس تنظیمات، اولویت‌بندی کند). در MVP همه انتساب‌های فعال برگردانده می‌شوند.

### ۳.۵. ساختار سازمانی کامل (برای کش) — `GET /api/v1/organizations/{id}/structure`
- **هدف:** دریافت کل درخت واحدها و پست‌های یک سازمان برای ساخت ماتریس دسترسی در سامانه ارجاعات.
- **پاسخ موفق (`200`):**
  ```json
  {
    "organizationId": "...",
    "name": "...",
    "posts": [ { "id": "...", "parentId": "...", "title": "...", "responsibilities": [...] } ]
  }
  ```
- **محدودیت:** فقط برای سازمان‌هایی که کاربر/سرویس به آن‌ها دسترسی دارد (بر اساس `OrganizationScope`).

## ۴. قوانین دسترسی و امنیت

1.  **احراز هویت:** تمام درخواست‌ها نیازمند `Bearer Token` معتبر IAM هستند.
2.  **مجوزها:**
    - سرویس ارجاعات باید دارای نقش/مجوزهایی باشد که اجازه خواندن ساختار سازمانی را داشته باشد (مثلاً `OrganizationStructure.Post.Read` یا معادل سرویسی آن).
    - اگر سامانه ارجاعات با توکن **کاربر** درخواست می‌دهد (Forwarded Token)، محدودیت‌های `OrganizationScope` کاربر اعمال می‌شود.
    - اگر با توکن **سرویس** درخواست می‌دهد، باید دسترسی کامل به ساختار (در حد مورد نیاز) داشته باشد.
3.  **خطاها:**
    - `401`: توکن نامعتبر.
    - `403`: دسترسی به سازمان/پست خارج از محدوده مجاز.
    - `404`: موجودیت یافت نشد.

## ۵. سناریوهای ارجاع و نگاشت به API

| سناریوی ارجاع | API مورد نیاز | توضیح |
|----------------|---------------|-------|
| ارجاع به رئیس | `GET /posts/{id}/manager` | مقصد = پست والد |
| ارجاع به هم‌سطح | `GET /posts/{id}/peers` | مقصد = یکی از پست‌های هم‌والد |
| ارجاع به زیرمجموعه | `GET /posts/{id}/subordinates` | بررسی عضویت مقصد در درخت |
| ارجاع بر اساس مسئولیت (مثلاً به مسئول دبیرخانه) | `GET /responsibilities/{code}/resolve` | مقصد = پست/پرسنل مسئول |
| بررسی حق مسئولیت (دسترسی به کل زیرمجموعه) | `GET /posts/{id}/subordinates` + بررسی `Responsibility` | اگر پست کاربر حق مسئولیت دارد، تمام درخت زیرمجموعه قابل مشاهده است |
